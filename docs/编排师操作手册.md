## 1. 角色概述

### 1.1 核心职责

编排师是用户与执行角色之间的唯一通信中枢，负责：
- 接收用户任务
- 组装输入包
- 调度Phase执行
- 处理返工
- 交付最终输出

### 1.2 禁止行为

- 禁止直接执行具体Phase（由对应角色执行）
- 禁止修改执行角色的输出
- 禁止跳过Phase
- 禁止绕过质量门禁

### 2.2 状态说明

| 状态 | 说明 | 可执行操作 |
|------|------|-----------|
| IDLE | 空闲，等待任务 | submit() |
| PHASE0_PENDING | Phase 0 执行中 | phase0_complete() / rework() |
| PHASE0_READY | Phase 0 完成 | start_phase1() |
| PHASE1_PENDING | Phase 1 执行中 | phase1_complete() / rework() |
| PHASE1_READY | Phase 1 完成 | start_phase1_5() |
| PHASE1_5_PENDING | Phase 1.5 执行中 | phase1_5_complete() / rework() |
| PHASE1_5_READY | Phase 1.5 完成 | start_phase2a() |
| PHASE2A_PENDING | Phase 2a 执行中 | phase2a_complete() / rework() |
| PHASE2A_READY | Phase 2a 完成 | start_phase2b() |
| PHASE2B_PENDING | Phase 2b 执行中 | phase2b_complete() / rework() |
| PHASE2B_READY | Phase 2b 完成 | deliver() |
| BLOCKED | 阻塞，等待问题解决 | resolve() |
| RESOLVED | 问题已解决 | 返回上一个状态 |
| DONE | 完成 | - |

### 2.3 状态转换规则

```javascript
// 状态转换伪代码

function submit(task) {
  if (current_state !== IDLE) {
    throw new Error("当前状态不允许提交新任务");
  }
  current_state = PHASE0_PENDING;
  task_id = generate_task_id();
  create_output_directory(task);
  return task_id;
}

function phase0_complete(report) {
  if (current_state !== PHASE0_PENDING) {
    throw new Error("Phase 0 未在执行中");
  }
  if (!validate_phase0_output(report)) {
    throw new Error("Phase 0 输出验证失败");
  }
  current_state = PHASE0_READY;
}

function start_phase1() {
  if (current_state !== PHASE0_READY) {
    throw new Error("Phase 0 未完成");
  }
  if (report.conclusion === "NEEDS_REVISION") {
    current_state = BLOCKED;
    return;
  }
  current_state = PHASE1_PENDING;
}

function rework() {
  if (rework_count >= 3) {
    throw new Error("返工次数已达上限");
  }
  rework_count++;
  current_state = BLOCKED;
}

function resolve() {
  current_state = previous_state;
  rework_count = 0;
}
```

## 3. 返工机制

### 3.1 返工触发条件

| 条件 | 说明 |
|------|------|
| 质量不达标 | 输出不符合质量标准 |
| 缺失信息 | 缺少必要信息，无法继续 |
| 用户要求 | 用户主动要求返工 |
| 规则违反 | 违反项目规则 |

### 3.2 返工上限

- **返工上限**：连续3次
- **超出上限**：报告用户，无法继续制作

### 3.3 返工流程

```
1. 检测到问题
       │
       ▼
2. 生成阻塞问题清单
       │
       ▼
3. 通知用户问题详情
       │
       ▼
4. 等待用户修改
       │
       ▼
5. 用户提交修改
       │
       ▼
6. 重新验证
       │
       ├─── 通过 ───▶ 继续下一Phase
       │
       └─── 失败 ───▶ 返工次数+1
                            │
                            ├─── < 3次 ──▶ 返回步骤2
                            │
                            └─── >= 3次 ──▶ 终止，报告用户
```

### 3.4 返工输出格式

每次返工生成 `阻塞问题清单.md`：

```markdown
# 阻塞问题清单

| 项目 | 内容 |
|------|------|
| 问题ID | BLOCK-{Phase}-{序号} |
| 严重度 | CRITICAL / HIGH |
| 描述 | 问题描述 |
| 建议解决 | 解决建议 |
| 状态 | OPEN |
```

```javascript
function can_start_phase(phase) {
  const inputs = get_required_inputs(phase);
  for (const input of inputs) {
    if (!file_exists(input.path)) {
      return { allowed: false, reason: `缺少输入文件: ${input.path}` };
    }
    if (!validate_input(input)) {
      return { allowed: false, reason: `输入验证失败: ${input.path}` };
    }
  }
  return { allowed: true };
}
```

## 7. 跨Phase反馈修正流程（v1.1 新增）

### 7.1 反馈触发条件

后续Phase发现前序Phase输出的问题时，触发反馈修正流程：

| 问题类型 | 来源Phase | 目标角色 |
|:---|:---|:---|
| 叙事偏离、人物描述问题 | Phase 1.5 / Phase 2a / Phase 2b | AI内容总导演（Phase 1） |
| 镜头序列问题（轴线、视线、节奏） | Phase 2a / Phase 2b | AI镜头序列设计师（Phase 1.5） |
| 视觉资产问题（人物四视图、场景资产） | Phase 2b | AI美术技术总监（Phase 2a/2b） |
| 合规问题 | 任意Phase | AI品控合规官（Phase 0） |

### 7.2 反馈路由规则

```
1. 问题接收
   编排师接收来自Phase 1.5、Phase 2a、Phase 2b的反馈
       │
       ▼
2. 问题分类
   编排师判断问题类型，对应到目标角色
       │
       ▼
3. 发送反馈
   编排师将问题清单发送给对应角色
       │
       ▼
4. 修正执行
   角色执行修正，完成后通知编排师
       │
       ▼
5. 重新调度
   编排师确认修正完成，按照Phase顺序重新调度
```

### 7.3 反馈拒绝处理

| 情况 | 处理方式 |
|:---|:---|
| 角色无法理解问题 | 编排师提供更具体的修改指引 |
| 角色认为问题不属于己责 | 编排师裁决归属，必要时升级用户判断 |
| 修正后仍不达标（≤2次反馈） | 允许再次反馈，最多2次/问题 |
| 修正后仍不达标（>2次反馈） | 升级为BLOCK问题，暂停流程，等待用户指示 |

### 7.4 反馈追踪表

| 问题ID | 问题类型 | 来源Phase | 目标角色 | 状态 | 反馈次数 | 解决时间 |
|:---|:---|:---|:---|:---|:---|:---|
| FEEDBACK-P1.5-001 | 叙事偏离 | Phase 1.5 | AI内容总导演 | OPEN/RESOLVED | 1 | - |
| FEEDBACK-P2A-001 | 视觉可行性 | Phase 2a | AI镜头序列设计师 | OPEN/RESOLVED | 1 | - |

### 7.5 反馈状态

| 状态 | 说明 |
|:---|:---|
| OPEN | 问题已接收，等待处理 |
| IN_PROGRESS | 角色正在修正 |
| RESOLVED | 问题已解决 |
| UPGRADED | 超过反馈次数上限，升级为BLOCK |

## 9. 版本联动检查机制（v1.2新增）

### 9.1 背景

Phase 1 的输出（人物清单.md、场景清单.md）在后续修复更新后，
Phase 2a 的输出可能与 Phase 1 的最新状态不一致。

典型问题案例：
- 人物清单.md 更新了吴为的肤色描述，但四视图仍为旧版本
- 场景清单.md 更新了约翰家的布局（三室一厅），但场景资产卡仍为两室一厅
- 村长增加了"花白胡须+弯曲木杖"，但四视图遗漏

### 9.2 触发条件

当以下任一情况发生时，**自动触发**版本联动检查提醒：

| 触发条件 | 检查内容 |
|---------|---------|
| 人物清单.md 版本更新 | 编排师通知美术技术总监验证四视图是否一致 |
| 场景清单.md 版本更新 | 编排师通知美术技术总监验证场景资产卡是否一致 |
| Phase 1.5 增强分镜执行表更新 | 编排师通知美术技术总监验证场景色调是否一致 |

### 9.3 编排师执行动作

```
检测到 Phase 1 版本更新
    │
    ▼
向美术技术总监发送"版本联动检查"提醒
    │
    ▼
等待美术技术总监确认：
    ├── 确认无需修改 → 记录版本映射，流程继续
    └── 确认需要修改 → 美术技术总监重新生成四视图/场景资产卡
                              │
                              ▼
                        更新输出文件版本号
                        记录新的版本映射关系
```

### 9.4 版本映射记录

每次 Phase 2a 完成后，编排师应记录版本映射：

```markdown
## 版本映射记录

| Phase 2a 输出 | 依据的 Phase 1 版本 |
|---------------|-------------------|
| 人物四视图Prompt包.md v1.1 | 人物清单.md v1.1 |
| 场景资产卡.md v1.1 | 场景清单.md v1.0 |
```

### 9.5 与返工机制的区别

| 机制 | 触发方式 | 处理方式 |
|------|---------|---------|
| 返工机制 | 下游Phase发现问题时触发 | 修正已生成的输出 |
| 版本联动 | 上游Phase版本更新时触发 | 主动复查，防患于未然 |
